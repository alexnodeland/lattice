# lattice-core

What lattice's packages share and must keep identical. artifactr, reflexr and grantr import none of one another, and relayr bridges artifactr and reflexr ([reflexr ADR-0003](../reflexr/adr/0003-independent-sibling-of-artifactr.md)). Where two of them would otherwise copy the same code, they depend on lattice-core, which imports no lattice package ([lattice ADR-0018](../adr/0018-lattice-core-what-the-libraries-share.md)).

!!! note "Not for applications"

    An application imports from the package it uses: each re-exports what it makes public from here, so its API is unchanged.

## The platform's contracts

v0.3 adds contracts every library must agree on, declared here as types, ports and fakes, and answered elsewhere, as integrations and settings are ([lattice RFC-0011](../rfcs/0011-the-v0-3-platform-capabilities-approvals-secrets-egress-and-adapters.md), [ADR-0032](../adr/0032-the-capability-registry-in-lattice-core-four-tiers-three-effects-and-entry-points.md)). They are new rather than moved from two packages, so they read ADR-0018 with ADR-0027 and ADR-0030: lattice-core declares the port and the registry, each library provides, and the application composes. Each imports only the standard library and pydantic, and each carries a version, `CONTRACT`, and publishes a JSON Schema in `packages/lattice-core/schemas/`, named by its major version and regenerated by `moon run lattice-core:schema`.

The registry only composes: it gates nothing and calls nothing. The enforcer is the path every call takes, and asks approvals of the store it is given, and `agents` offers capabilities to pydantic-ai agents through it. artifactr's provider is the first library's ([artifactr ADR-0099](../artifactr/adr/0099-artifactrs-tools-as-capabilities-called-through-the-enforcer-whose-policy-asks-approval.md)), and lattice's enforcement suite (`tests/test_enforcement_suite.py`) holds it and a fake of each kind to the enforcer; nothing else calls through either yet. grantr's store of approvals answers the `Approvals` port, the first answer winning on every storage ([grantr ADR-0038](../grantr/adr/0038-approvals-stored-per-tenant-answered-by-grantrs-subjects-groups-and-grants.md)). The secrets, egress and adapters contracts only declare: nothing reads a secret, decides an egress or enables an adapter yet. The conformance harness checks the fake secrets store against the secrets suite; the other libraries' providers, the secrets adapters, Envoy and its authorizer, and `make validate` come in the next pull requests of RFC-0011's phases.

A library names its provider in its `pyproject.toml`:

```toml
[project.entry-points."lattice.capabilities"]
artifactr = "artifactr.capabilities:provider"
```

and an application composes `Registry(*discover())`, or passes its providers by hand, as tests always do. Installing a provider never turns anything on: the enforcement path offers and calls a capability only where its gate's integration is on (ADR-0027).

## What belongs here

Only infrastructure that is the same in two or more packages, word for word but for their names, and must stay the same. Code that only looks alike stays where it is, and nothing about a package's domain belongs here. lattice-core changes only by addition and deprecation, and each package requires a lower bound of it.

## Installing it

You don't install it yourself: the packages that need it require it. Its distribution is `lattice-core-ai`, since the name `lattice-core` on PyPI is an unrelated project, and it is imported as `lattice_core`. It is on PyPI, from 0.1.0. A package installed from lattice with uv takes it from the same commit; pip takes it from PyPI.
