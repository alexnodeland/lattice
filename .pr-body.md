## What

portalr's guides (phase 8), tested against the code, and a regression guard for #172. The branch now has main merged in (a merge commit, no force-push), and the guides are brought up to date with what landed since.

### 1. `docs(portalr)`: the guides

portalr's guides, from the behaviour that is built, in `docs/portalr/`:

- **Getting started:** install the wheel (a release's, or built from a checkout; a git install has no UIs), mount the router (a runnable example, now with the `people` hook), `config.json` (now with `people`), portalr's three actions, and sign-in. It says what stackr's template now does for you.
- **The app:** tenants and workspaces, threads and chat, restricting and sharing a thread (people by email where the application names them), artifacts, proposals, runs, rules.
- **The admin UI:** home (Near budget and Over budget), access (people by email, or a short id), audit, feedback, usage, traces, logs and health, runs (status colours with a shape and a word). Admin is compact; a chart's figures are a table under "Show the figures".
- **An operator's runbook:** what the stack gives the portal (the spend-read key from `make portal-key`, never the master key; on a single host, sign-in on `app.<domain>` with Caddy's three-call allow-list, and invitations off), creating a tenant, the deployment audit (now with tenant creations), Tools, and what is recorded and for how long.
- **What portalr keeps from view:** what is withheld by default and how to ask for it, what isn't withheld, emails (who sees whose through `GET /portalr/v1/people`, and how long the server and browser keep them), the browser, and where the gate stops.

The section's navigation gains the guides and the decision records 0019 to 0039. `index.md` and the README say what is built and what is not.

### 2. `test`: a guard for #172 (the issue stays open)

#172's first sign-in flake is `net::ERR_NETWORK_CHANGED`: Chromium on Linux fails every in-flight request, even to 127.0.0.1, when a network interface comes or goes, so the sign-in page's chunks fail and the Email field never renders. #168 made CI run `bdd` one project at a time (`ONE_AT_A_TIME`), so one UI's stack no longer comes down while the other's Chromium loads. #254 has the same mechanism for the browser unit tests, and #256 addresses it there. Neither covers the interface changes the scenarios' own compose stack, or other Docker activity in the Acceptance job, can still make, so **this PR does not fix or close #172**.

This commit makes the part that is fixed hard to reintroduce: `batches()` is a function, and `tests/test_affected.py` holds every task that runs `scripts/bdd` to `ONE_AT_A_TIME`. Its limit: it matches the literal `scripts/bdd` (`STACK_SCRIPTS`), so a stack started another way (stackr's `scripts/smoke`, `examples/`) is not caught. Its docstring carries a `TODO(#172)` for the remaining cause. It adds no retry and touches no timeout.
