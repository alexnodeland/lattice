# AGENTS.md

Instructions for coding agents working in lattice. Humans read [CONTRIBUTING.md](CONTRIBUTING.md), which is the authority; this file is the short version, and each directory with rules of its own has an `AGENTS.md` of its own. The nearest one to the file you are editing wins where they disagree; read it, and every one above it, before you change anything.

## What this repository is

One repository: eight Python packages, two reference implementations, and the tools that check, release and document them ([docs/architecture.md](docs/architecture.md)).

| Path | What it is |
|---|---|
| `packages/artifactr/` | Versioned artifacts that people and agents share; agents propose, people accept |
| `packages/reflexr/` | Rules over event streams that run agents, graphs and functions |
| `packages/evalr/` | Typed evaluations that learn from people's feedback |
| `packages/relayr/` | Carries events from artifactr (and task trackers) to reflexr |
| `packages/grantr/` | Identity and access, checked before every command and read |
| `packages/portalr/` | The portal: a Python package, and `web/`, its Bun workspace |
| `packages/stackr/` | The stack (compose, deploy) and the copier application template |
| `packages/lattice-core/` | What the libraries share and must keep identical |
| `examples/` | `docplan` (artifactr's reference implementation) and `oncall` (reflexr's) |
| `docs/` | The documentation site: lattice's pages, and `docs/<package>/` for each package |
| `scripts/` | The repository's tools: affected projects, acceptance tests, API breaks, releases |
| `tests/` | lattice's own tests: the quality gates over all the Python, and moon's edges |

## Setup and commands

The toolchain is pinned in `.prototools` (`proto use`): uv, Bun, moon. Don't use pip, npm, pnpm or Node.js.

```bash
make install                      # everything, in one environment
moon run <project>:<task>         # e.g. moon run artifactr:test
moon run :check                   # every project's checks, as CI runs them
make check                        # the same
moon project <project>            # list a project's tasks
```

Python projects have `lint`, `typecheck`, `test`, `format`, `check`; web packages the same through Bun, plus `build`. Run `moon run <project>:format` and then `moon run <project>:check` for every project you touched before you call a change done. A focused test run is `uv run pytest packages/<pkg>/tests/<file>.py -n0`.

## Rules that CI enforces

- **100% branch coverage** of every package's `src/`. A change without tests for each branch fails.
- **pyright strict** for `src/` and `scripts/`; TypeScript strict and Biome in the web packages.
- **No inline suppressions, anywhere:** no `# type: ignore`, `# pyright: ignore`, `# noqa`, `# pragma: no cover`, `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, `biome-ignore`. Restructure the code; `tests/test_quality.py` fails on any.
- **Warnings are errors** in tests, and tests run in a random order (pytest-randomly). Don't rely on test order or shared state.
- **The libraries stay independent.** Each library's layering test lists what each module may import; deptry fails on an undeclared import; `standalone` installs each wheel outside the workspace. Don't import one library from another unless its `pyproject.toml` already declares it. Shared infrastructure belongs in `lattice-core` ([ADR-0018](docs/adr/0018-lattice-core-what-the-libraries-share.md)).
- **Generated files must not drift.** JSON Schemas, OpenAPI documents, Grafana dashboards and the client's types are regenerated by `<project>:schema`, `<project>:dashboards` and `client:types`; never edit them by hand.
- **Public APIs are checked for breaks** against the last release (`moon run lattice:breaks`). A break needs `!` in the PR title and a `BREAKING CHANGE:` footer.

## Conventions

- Google-style docstrings and full type annotations on public API.
- Dependency ranges in `pyproject.toml` are the *oldest* versions supported; raise a floor only with the code that needs it. `uv.lock` and `bun.lock` pin what runs. Web packages pin exact versions.
- Settings are typed, declared in lattice-core and only narrowed below ([ADR-0030](docs/adr/0030-settings-typed-declared-in-lattice-core-and-only-narrowed-below.md)).
- Markdown renders on GitHub and on the docs site (Python-Markdown): a blank line before every list, and nested items indented by the parent's text (two spaces after `-`, three after `1.`).
- Don't edit any `CHANGELOG.md`; release-please writes them.
- Accepted ADRs are not edited. A changed decision gets a new ADR that supersedes the old one. Architecture docs (`docs/<package>/architecture.md`) are updated in the same PR as the code they describe.

## Commits and pull requests

- Branch from `main`; keep PRs small and short-lived. A change that spans packages lands in one PR.
- Commits and PR titles are [Conventional Commits](https://www.conventionalcommits.org/): `feat(core): ...`, `fix(gateway): ...`, `docs(adr): ...`. Scopes are a package's module or area names.
- PRs are squash-merged through Mergify's queue (the `queue` label). Don't push to `main`.
- Definition of done: tests cover the change, `make check` passes, public API is documented, architecture docs match, new decisions have an ADR.

## Safety

- Commands that start Docker compose projects (`*:api`, `*:bdd`, `*:image`, `*:pg-up`) name them with a random token; remove a leftover one only by its exact name (`docker compose -p <name> down --volumes`).
- Never commit secrets; `detect-private-key` runs in pre-commit. Security issues go through [SECURITY.md](SECURITY.md), not public issues.
